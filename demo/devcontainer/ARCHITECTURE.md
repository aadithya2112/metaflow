# Devcontainer Prototype Architecture

This prototype hooks into Metaflow at the same execution seam used by the existing compute decorators: `StepDecorator.runtime_step_cli`. That hook is important because it lets a step decorator rewrite the command that the local runtime launches for a task without changing how the rest of the flow is scheduled. In this demo, `@devcontainer` changes the task launch from the normal `step` command to `devcontainer step`, which gives us a host-side interception point that is visible in logs and easy to explain in a proposal.

The `devcontainer step` command is intentionally small. It does not try to reimplement Metaflow task execution. Instead, it reconstructs the original `python -u <flow> step ...` command, derives the workspace from the local `.metaflow` datastore root, bind-mounts that workspace into Docker at `/workspace`, and runs the original step command inside the container. Before launch, it also writes a minimal `devcontainer.json` under the local `.metaflow` tree that captures the same image, environment, mounts, and run arguments the demo launcher is using. Because the flow code and the `.metaflow` datastore are both visible inside the container, the task can write artifacts exactly where downstream host-side steps expect to find them.

That bind-mounted local datastore is the key MVP simplification. It avoids code packaging, remote metadata sync, and custom artifact bridges while still proving the riskiest architectural point: redirected container execution can preserve Metaflow semantics. The generated `devcontainer.json` is deliberately descriptive only in this version. It is the smallest step toward the project requirement in `gsoc-project.md` without replacing the already-working Docker launcher. The prototype therefore demonstrates real execution redirection, real container isolation, real artifact continuity, and now a concrete, inspectable devcontainer config artifact.

The full project would generalize each part of this. The decorator would grow from a Docker-only proof to a real `devcontainer.json`-driven abstraction. The launcher would need richer environment capture, support for generated container specs, and optional backends like DevPod or Daytona. Security controls such as network isolation and read-only mounts would become explicit decorator settings. But the core idea would stay the same: let Metaflow decide *what* task to run, and let `@devcontainer` decide *where* that task command executes.
